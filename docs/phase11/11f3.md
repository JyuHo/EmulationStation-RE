## Objectif

Reliquat de 3.D (`PROMPT.md` 0.2, 0.3, 14 « Pièges ») : `Window` possède les GUI empilées, mais
elles se ferment encore elles-mêmes par `delete this`. Cette PR remplace **chaque** `delete
this` d'une GUI par une fermeture demandée à `Window`. **Aucun changement visible** : mêmes
écrans, même ordre, mêmes rappels.

Pourquoi c'est risqué : #6 avait fait supprimer la GUI par `Window::removeGui` alors que
`delete this` restait, et chaque fermeture de menu libérait deux fois la mémoire. D'où les
règles ci-dessous, et asan sur chaque étape.

## Conception imposée

Modèle de Recalbox (`guis/Gui.h:40-46` : `Close()` marque la GUI, la boucle principale la
supprime plus tard), adapté à la propriété par `unique_ptr` du projet :

- `void Window::closeGui(GuiComponent* gui)` : retire **tout de suite** le `unique_ptr` de
  `mGuiStack` (la GUI ne reçoit plus d'entrée, n'est plus dessinée, `peekGui()` ne la rend plus,
  l'aide de la nouvelle GUI du dessus est mise à jour comme dans `removeGui`) et le **garde
  vivant** dans une liste `mClosedGuis`. GUI absente de la pile : rien (pas d'erreur, pas de
  double fermeture).
- La liste `mClosedGuis` est vidée (destruction réelle) au **début** de `Window::update` et dans
  `~Window`. Ainsi le code qui suit `closeGui(this)` dans une méthode de la GUI travaille encore
  sur un objet vivant.
- Vider la liste : déplacer d'abord son contenu dans une variable locale, puis la détruire
  (un destructeur peut fermer une autre GUI ou en ouvrir une).
- `Window::removeGui` et son appel dans `~GuiComponent` **restent** : ils protègent une GUI
  détruite autrement, et `test_Window.cpp` (« a GUI that deletes itself… ») les fixe (R7 : ce
  test ne change pas).
- Un composant non empilé qui se supprimait lui-même : voir `AsyncReqComponent` ci-dessous ;
  **STOP** si tu en trouves un autre.

## Tests (chaque `TEST_CASE` ajouté porte l'étiquette `[11f3]`)

Dans `test_Window.cpp`, avec `CountingGui` (existant) :
- `closeGui` d'une GUI du dessus : `peekGui()` rend aussitôt celle d'en dessous, la GUI fermée
  n'est **pas encore** détruite (compteur à 0), elle l'est après `update(0)` (compteur à 1).
- Une GUI qui appelle `closeGui(this)` dans sa propre méthode puis lit un de ses membres :
  aucun rapport asan.
- `closeGui` deux fois de suite sur la même GUI : une seule destruction.
- `closeGui` d'une GUI qui n'est pas au sommet (cas de `GuiScraperMulti`) : retirée, l'ordre
  des autres est gardé.
- Une GUI dont le destructeur ferme une autre GUI ou en empile une nouvelle : aucune double
  destruction, pile cohérente.
- `~Window` avec des GUI fermées non encore détruites : chacune détruite une fois.
- Les deux tests existants restent identiques et verts.
